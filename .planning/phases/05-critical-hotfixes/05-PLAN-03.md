<objective>
Two-step fix for promo usage tracking (per D-03):

1. Add `promo_code TEXT` column to the `checkouts` table via `safeMigrate()` in `db.js` — prevents column-not-found crash when the route tries to INSERT the field.
2. Update `POST /api/checkouts` in `checkouts.js` to (a) accept `promo_code` from request body, (b) include it in the INSERT, and (c) run `UPDATE promo_codes SET times_used = times_used + 1 WHERE code = ? AND is_active = 1` after the INSERT when a promo code is present.

Purpose: `times_used` is currently never incremented, making promo usage limits unenforced. This is the commit point locked by D-03.
Output: `backend/db.js` with one new safeMigrate call; `backend/routes/checkouts.js` with promo_code extraction, INSERT inclusion, and post-INSERT increment.

From backend/db.js lines 309–320 — transaction() helper (available if needed):
```javascript
function transaction(fn) {
  try {
    _db.run('BEGIN TRANSACTION');
    const result = fn();
    _db.run('COMMIT');
    _save();
    return result;
  } catch (err) {
    _db.run('ROLLBACK');
    throw err;
  }
}
```
Note: sql.js is single-threaded in-memory — a separate sequential prepare().run() is safe without transaction wrapping. Either approach is acceptable; use the simpler sequential approach unless the executor judges wrapping beneficial.
