<objective>
Add database-level idempotency for Razorpay payments. Two changes:
1. `db.js`: Add `safeMigrate('CREATE UNIQUE INDEX IF NOT EXISTS idx_orders_razorpay_payment_id ON orders(razorpay_payment_id) WHERE razorpay_payment_id IS NOT NULL')` after the existing safeMigrate calls. The partial index ensures only non-NULL payment IDs are unique — UPI/COD orders with NULL payment IDs are unaffected.
2. `payments.js`: Update the `/verify` endpoint catch block to return 409 on `UNIQUE constraint` errors instead of the generic 500.

Purpose: The existing application-level SELECT-before-INSERT check (payments.js lines 258-264) has a TOCTOU race window: two concurrent requests can both pass the SELECT check and then both attempt the INSERT. The DB UNIQUE INDEX eliminates this race. The 409 response on the catch block provides a correct client-facing signal for duplicate payments.

Output: db.js with partial UNIQUE INDEX on orders; payments.js verify handler returning 409 on UNIQUE constraint errors.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Razorpay client redirect → POST /api/payments/verify | Payment verification from customer browser after Razorpay checkout |
| Concurrent requests → db.js orders table | Two simultaneous verifications for the same payment_id |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-04-01 | Tampering | POST /api/payments/verify — TOCTOU race | mitigate | DB UNIQUE INDEX eliminates the race window between SELECT check and INSERT — second INSERT throws UNIQUE constraint error |
| T-06-04-02 | Tampering | Duplicate order creation | mitigate | Application-level check (fast path) + DB constraint (safety net) — defense in depth, neither alone is sufficient |
| T-06-04-03 | Denial of Service | Constraint error → 500 → Razorpay retry | mitigate | 409 on UNIQUE constraint prevents Razorpay's webhook retry from treating duplicate as an unprocessed event |
| T-06-04-04 | Tampering | NULL payment_ids (UPI/COD) | accept | Partial index (`WHERE razorpay_payment_id IS NOT NULL`) allows multiple NULL rows — UPI/COD orders have their own dedup via UTR check at lines 298-300 |
</threat_model>
